## Deployment Environments

### 1. Development (Local)

**Purpose**: Local development and testing by individual developers

**Configuration**:
- **Location**: `localhost`
- **URLs**:
  - Student App: `http://localhost:3000`
  - Admin App: `http://localhost:3001`
  - Superadmin App: `http://localhost:3002`
  - Email Backend: `http://localhost:5000`

**Database**: Development Firebase project or emulators

**Access**: All developers

**Deployment**: Manual (`npm start`)

---

### 2. Staging (Preview)

**Purpose**: Pre-production testing and client review

**Configuration**:
- **Location**: Vercel Preview Deployments
- **URLs**: Auto-generated by Vercel
  - Example: `student-app-git-feature-branch.vercel.app`

**Database**: Staging Firebase project

**Access**: Development team, QA testers, client reviewers

**Deployment**: Automatic on PR creation

**Characteristics**:
- Mirrors production configuration
- Test data only
- Can be reset periodically

---

### 3. Production (Live)

**Purpose**: Live system used by students, staff, and administrators

**Configuration**:
- **Location**: Vercel Production + Firebase
- **URLs**:
  - Student App: `https://asj-student.vercel.app`
  - Admin App: `https://asj-admin.vercel.app`
  - Superadmin App: `https://asj-superadmin.vercel.app`

**Database**: Production Firebase project (`academia-de-san-jose`)

**Access**: End users (students, staff, admins)

**Deployment**: Automatic on merge to `main` branch

**Characteristics**:
- Real student and request data
- High availability required
- Changes require approval

## Deployment Process/Pipeline

### CI/CD Tools Used

**Frontend (React Apps)**:
- **Platform**: Vercel
- **CI**: Automatic build on every push
- **CD**: Automatic deploy to production on merge to `main`
- **Testing**: Manual testing

**Backend (Firebase Functions)**:
- **Platform**: Firebase
- **CI**: Manual linting (`npm run lint`)
- **CD**: Manual deployment (`firebase deploy --only functions`)

**Email Backend (Node.js/Express)**:
- **Platform**: Manual deployment (if using VPS)
- **CI**: None
- **CD**: Manual via SSH and PM2/systemd

---

### Automated Steps

#### Frontend Deployment (Vercel)

1. **Push to GitHub**:
   ```bash
   git push origin feature/new-feature
   ```

2. **Vercel Automatically**:
   - Detects push
   - Runs `npm install`
   - Runs `npm run build`
   - Deploys to CDN
   - Generates preview URL

3. **Deployment Complete**:
   - Preview URL available in ~2 minutes
   - Vercel bot comments on PR with URL

---

### Manual Steps

#### Firebase Functions Deployment

1. **Test Locally**:
   ```bash
   cd functions
   npm run serve
   ```

2. **Lint Code**:
   ```bash
   npm run lint
   ```

3. **Deploy**:
   ```bash
   firebase deploy --only functions
   ```

4. **Verify**:
   ```bash
   firebase functions:log
   ```

---

#### Email Backend Deployment (If Using VPS)

1. **SSH to Server**:
   ```bash
   ssh user@server-ip
   ```

2. **Pull Latest Code**:
   ```bash
   cd /var/www/email-backend
   git pull origin main
   ```

3. **Install Dependencies**:
   ```bash
   npm install --production
   ```

4. **Restart Service**:
   ```bash
   pm2 restart email-backend
   ```

---

### Standard Deployment Flow

```
1. Feature Development
   ├── Create feature branch from develop
   ├── Develop and test locally
   └── Push to GitHub → Vercel creates preview

2. Code Review
   ├── Create PR to develop
   ├── Request peer review
   └── Approve and merge

3. Staging Deployment
   ├── Merge to develop
   ├── Auto-deploy to staging
   └── Test in staging environment

4. Production Release
   ├── Create PR from develop to main
   ├── Final review and approval
   ├── Merge to main
   └── Auto-deploy to production

5. Post-Deployment
   ├── Monitor logs
   └── Verify functionality
```

## Branching Strategy

### Git Flow Model

We use a simplified Git Flow model:

```
main (production)
  ├── develop (staging)
  │     ├── feature/qr-code-login
  │     ├── feature/ai-moderation
  │     └── bugfix/password-reset
  └── hotfix/critical-security-fix
```

---

### Branch Types

#### 1. `main` Branch

**Purpose**: Production-ready code

**Deploys To**: Production (automatically)

**Protection Rules**:
- ✅ Requires pull request
- ✅ Requires 1 approval
- ❌ Direct commits forbidden

**Merge Sources**:
- `develop` branch (regular releases)
- `hotfix/*` branches (emergency fixes)

---

#### 2. `develop` Branch

**Purpose**: Integration branch for features

**Deploys To**: Staging (automatically)

**Protection Rules**:
- ✅ Requires pull request (recommended)
- ⚠️ Direct commits allowed (for quick fixes)

**Merge Sources**:
- `feature/*` branches
- `bugfix/*` branches

---

#### 3. `feature/*` Branches

**Purpose**: New feature development

**Deploys To**: Preview deployment (Vercel)

**Lifecycle**:
1. Branch from `develop`
2. Develop feature
3. Create PR to `develop`
4. Review and merge
5. Delete branch

**Naming Convention**:
```
feature/qr-code-login
feature/ai-content-moderation
feature/notification-system
```

**Format**: `feature/[description-in-kebab-case]`

---

#### 4. `bugfix/*` Branches

**Purpose**: Non-critical bug fixes

**Deploys To**: Preview deployment (Vercel)

**Lifecycle**: Same as feature branches

**Naming Convention**:
```
bugfix/password-reset-expiry
bugfix/notification-duplicate
bugfix/qr-scan-failure
```

**Format**: `bugfix/[description-in-kebab-case]`

---

#### 5. `hotfix/*` Branches

**Purpose**: Critical production bug fixes

**Deploys To**: Production (after merge to `main`)

**Lifecycle**:
1. Branch from `main`
2. Fix critical bug
3. Create PR to `main` (expedited review)
4. Merge to `main` → Auto-deploy to production
5. Merge back to `develop`
6. Delete branch

**Naming Convention**:
```
hotfix/security-vulnerability
hotfix/data-corruption
hotfix/authentication-failure
```

**Format**: `hotfix/[description-in-kebab-case]`

**⚠️ Use Only For**:
- Security vulnerabilities
- Data loss/corruption issues
- Complete system outages
- Critical authentication failures

---

### Branch-to-Environment Mapping

| Branch Type | Deploys To | Trigger | Approval Required |
|-------------|------------|---------|-------------------|
| `main` | **Production** | Merge to main | ✅ Yes (1 approval) |
| `develop` | **Staging** | Merge to develop | ⚠️ Recommended |
| `feature/*` | **Preview** | Push to branch | ❌ No |
| `bugfix/*` | **Preview** | Push to branch | ❌ No |
| `hotfix/*` | **Production** | Merge to main | ✅ Yes (expedited) |

## Approval & Review Requirements

### Pull Request to `develop` (Staging)

**Required**:
- ✅ At least 1 peer review (recommended)
- ✅ All discussions resolved
- ⚠️ Manual testing completed

**Reviewers**: Any team member

**Review Focus**:
- Code quality
- Functionality
- No obvious bugs

---

### Pull Request to `main` (Production)

**Required**:
- ✅ **1 approval from senior developer or tech lead**
- ✅ Staging testing completed
- ✅ All discussions resolved

**Reviewers**: 
- Senior Developer
- Tech Lead
- Project Manager (for major features)

**Review Checklist**:
- [ ] Code follows naming conventions
- [ ] No secrets in code
- [ ] Environment variables documented
- [ ] Documentation updated
- [ ] Tested in staging
- [ ] No breaking changes (or documented)

---

### Hotfix Approval (Expedited)

**Required**:
- ✅ **1 approval** (can be expedited)
- ✅ Brief explanation of issue
- ✅ Evidence of testing

**Process**:
1. Create hotfix branch from `main`
2. Fix critical issue
3. Test fix thoroughly
4. Create PR with "HOTFIX" label
5. Request expedited review
6. Merge and deploy immediately
7. Monitor closely

## Rollback Procedures

### Vercel Rollback (Frontend Apps)

#### Method 1: Vercel Dashboard (Recommended)

**Steps**:
1. Go to Vercel Dashboard
2. Select the project (e.g., `student-app`)
3. Click **Deployments** tab
4. Find the last working deployment
5. Click **⋮** → **Promote to Production**
6. Confirm rollback

**Time**: ~30 seconds

**Impact**: Instant rollback to previous version

---

#### Method 2: Git Revert

**Steps**:
```bash
# Find the bad commit
git log --oneline

# Revert the commit
git revert <commit-hash>

# Push to trigger new deployment
git push origin main
```

**Time**: ~2-3 minutes (includes rebuild)

**Impact**: Creates new commit that undoes changes

---

#### Method 3: Redeploy Previous Tag

**Steps**:
```bash
# Checkout previous release tag
git checkout v1.2.0

# Create rollback branch
git checkout -b rollback-to-v1.2.0

# Push and create PR
git push origin rollback-to-v1.2.0
```

**Time**: ~5 minutes (includes review and merge)

**Impact**: Returns to specific tagged version

---

### Firebase Functions Rollback

#### Method 1: Redeploy Previous Version

**Steps**:
```bash
# Checkout previous working version
git checkout v1.2.0

# Deploy functions
cd functions
firebase deploy --only functions

# Return to main branch
git checkout main
```

**Time**: ~2-5 minutes

**Impact**: Redeploys previous function code

---

#### Method 2: Code Revert

**Steps**:
```bash
# Revert problematic code
cd functions
git revert <commit-hash>

# Deploy immediately
firebase deploy --only functions
```

**Time**: ~2-5 minutes

**Impact**: Reverts specific commit

---

### Email Backend Rollback (If Using VPS)

#### Manual Rollback

**Steps**:
```bash
# SSH to server
ssh user@server-ip

# Navigate to backend directory
cd /var/www/email-backend

# Checkout previous version
git checkout v1.2.0

# Restart service
pm2 restart email-backend
```

**Time**: ~2 minutes

**Impact**: Reverts backend to previous version

---

### Database Rollback (Firestore)

**⚠️ No Built-in Rollback** - Firestore doesn't have automatic rollback

**Options**:

#### Option 1: Manual Data Correction
- Identify affected documents
- Manually update/delete via Firebase Console
- Use Firebase Admin SDK for bulk operations

#### Option 2: Restore from Backup
- Use Firestore export (if configured)
- Restore entire collection or specific documents
- **Requires prior backup setup**

**Prevention**:
- Always test database operations in staging first
- Use Firestore security rules to prevent bad writes
- Implement soft deletes (never hard delete)

---

### Rollback Communication

**Immediate Actions**:
1. **Notify Team**: Post in team chat
2. **Execute Rollback**: Follow appropriate procedure
3. **Verify**: Confirm system is working
4. **Document Issue**: Record what went wrong

**Communication Template**:
```
🚨 ROLLBACK INITIATED

Reason: [Brief description of issue]
Affected: [Which apps/services]
Action: Rolling back to version [v1.2.0]
Status: [In Progress / Complete]

Incident owner: [Name]
```

## Summary

### Key Points

1. **Environments**:
   - Development (local) → Staging (preview) → Production (live)

2. **Deployment**:
   - **Frontend**: Automatic via Vercel
   - **Backend**: Manual via Firebase CLI

3. **Branching**:
   - `main` → Production
   - `develop` → Staging
   - `feature/*` and `bugfix/*` → Preview
   - `hotfix/*` → Emergency production fixes

4. **Approvals**:
   - Staging: Peer review recommended
   - Production: 1 approval required
   - Hotfix: Expedited approval

5. **Rollback**:
   - **Vercel**: Instant via dashboard
   - **Firebase**: Redeploy previous version
   - **Database**: Manual correction only
